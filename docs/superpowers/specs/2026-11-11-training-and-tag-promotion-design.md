# Этап 2: от собранных данных к модели и стандартным тегам — дизайн

Статус: на согласование. Предыдущий этап: `docs/superpowers/specs/2026-11-11-training-data-contribution-design.md`
(сбор данных; приёмник `https://contribute.sampledicer.pro`).

## Зачем

Сбор работает: подтверждённые типы, теги, тональность и темп с согласия уходят в R2. Дальше данные
должны превращаться в улучшение продукта, иначе этап 1 бессмыслен. Два бэклоговых пункта:

- пункт 12: обучение по пользовательским библиотекам;
- пункт 13: перенос частых кастомных тегов и типов в стандартные.

Цель этапа — замкнуть цикл «выгрузка → проверка → обучение → поставка в билд → стандартные теги»
так, чтобы он стоил $0 и не добавлял в приложение ни одного сетевого вызова.

## Цели

1. Детерминированная, воспроизводимая сборка глобальных прототипов из `contribute.jsonl`.
2. Оценка качества до поставки: сравнение с текущим поведением на отложенных установках.
3. Приложение получает прототипы из билда, без скачивания; локальные подтверждения пользователя
   по-прежнему важнее глобальных.
4. Список кандидатов в стандартные теги и типы с частотой, покрытием установок и решением владельца.
5. Датасет и модель пересобираются из R2, поэтому удаление данных попадает в следующий выпуск.

## Не цели

- ONNX-модель и замена DSP-правил. Прототипы используют существующий `AdaptiveClassifier`.
- Автоматическое добавление тегов в стандартные без просмотра.
- Обучение в облаке, GPU, платные сервисы.
- Новые сетевые вызовы в приложении.

## Анти-цели

- В репозиторий попадают аудио, пути, имена файлов или установок.
- Прототип с одной установки влияет на всех.
- Новая версия прототипов ухудшает точность на отложенных установках, а её всё равно поставляют.
- Пользователь не может отличить в UI, откуда взялся тип: из его подтверждений или из общей модели.

## Ограничения

- Форма признаков — 14 чисел 0..1, `featureSchema = 1` (`AdaptiveClassifier::extractFeatures`).
- `AdaptiveClassifier` держит прототипы в памяти; источник — `ml_feedback_samples` (схема 13).
- Бинарник собирается из репозитория; статический ресурс уже есть (`BinaryData`).
- Данные в R2 обезличены, у записи есть `recordId` и `installId` только в пачке.
- Бесплатный лимит R2: 10 GB; ожидаемый объём — единицы мегабайт.

## Подходы

| Подход | Что даёт | Цена | Итог |
|---|---|---|---|
| **Глобальные прототипы в билде** | учится на всех, работает на существующем коде, ноль сети | нужна пересборка на каждый выпуск | **рекомендуется** |
| ONNX-классификатор | богаче; но нужен датасет на порядок больше, обучение и веса в бандле | десятки МБ, сложнее отладка, качества на старте нет | позже, когда данных станет много |
| Дообучение на устройстве поверх глобальных | персонализация без сети | уже есть: локальные прототипы и так главнее | входит в этот этап как приоритет |

## Части

### 0. Происхождение записи (схема 14)

Проверка кода показала: `ml_feedback_samples` пишут два разных пути. Пользовательский — правка типа
(`applyTypeOverride`), назначение тега (`assignTagAndRemember`). Машинный — `AutoTagService` и
пакетное применение авто-тегов: там тип берётся из `smart_results` (`dsp_acoustic`, `path` и т.п.),
а теги — все текущие. Если такие строки учить как подтверждённые, модель будет учиться на своих же
догадках, а `installSupport` посчитает одну установку многократно.

Поэтому в схему 14 добавляется столбец `origin TEXT NOT NULL DEFAULT 'legacy'`:

- `user` — строка записана по действию пользователя;
- `auto` — записана AutoTag или пакетным применением;
- `legacy` — записана до схемы 14, происхождение неизвестно.

`recordFeedback` получает аргумент `origin`; оба машинных вызова передают `auto`, оба
пользовательских — `user`. Выгрузка отправляет только `user`; `auto` и `legacy` остаются локально.
Строки `legacy` не удаляются и не переписываются — они просто не участвуют в обучении.

### 1. Выгрузка и проверка (`services/contribute-worker/scripts/export.mjs`)

Скрипт уже собирает `contribute.jsonl`, применяет надгробия и оставляет последнюю версию записи по
`recordId`. Добавляется:

- `--stats` — сводка в JSON: число установок, записей, распределение по типам, по тегам, доля
  кастомных меток, средняя поддержка на метку;
- `--min-installs N` (по умолчанию 3) — метка попадает в отчёт только при подтверждении с N разных
  установок;
- `report.md` рядом с датасетом: те же числа таблицей, для просмотра глазами;
- отказ работать при `featureSchema`, которого нет в коде (защита от рассинхронизации);
- проверка диапазонов: любое значение вне 0..1 или `NaN` останавливает выгрузку;
- в пачку не попадает `origin` (это решает клиент), но пачка приходит только из строк `user`

Проверки в Node-тестах на фикстуре из нескольких пачек: дубли `recordId`, надгробия, фильтр установок.

### 2. Обучение прототипов (`services/training/`, Node, без зависимостей)

Вход — `contribute.jsonl`, выход — `resources/ml/global_prototypes.json`.

```json
{
  "schema": "prototypes.v1",
  "featureSchema": 1,
  "generatedAt": "2026-11-11T00:00:00Z",
  "records": 4200,
  "installs": 37,
  "labels": [
    { "label": "kick", "kind": "type", "support": 310, "installSupport": 21,
      "prototypes": [[0.02, 0.11, "...14 чисел"]] }
  ]
}
```

Правила:

- метка (тип или тег) берётся, если её подтвердили `installSupport >= 3` и `support >= 10`;
- на метку — до 8 прототипов, отбор farthest-first (детерминированный порядок: сортировка по
  `recordId`), поэтому выбросы не становятся центроидами;
- не более 200 меток на вид; при переполнении — по убыванию `installSupport`;
- вес прототипа — `support` и `installSupport`, для аудита;
- округление как в отправке (0.001), сортировка ключей — байт-в-байт воспроизводимый файл.

Оценка перед поставкой: leave-one-install-out, и сравнение повторяет то, что делает приложение.

- «Было» — только локальные прототипы установки (текущее поведение без глобальных).
- «Стало» — локальные плюс глобальные из остальных установок, с тем же штрафом 0.95 и правилом
  приоритета, что и в билде.
- Метрика типа: top-1 совпадение метки; дополнительно по группам (`percussion`, `tonal`, `vocal`,
  `fx`, `other`), список групп лежит рядом со скриптом и не меняется без записи в отчёте.
- Метрика тегов: top-3 предсказанных тегов против набора тегов записи, precision и recall микро
  (по всем встречам тегов), а не «top-1».

Файл `training-report.md`: число установок и записей, точность по типу «было / стало» целиком и по
группам, precision/recall тегов, худшие 10 меток. Порог: точность «стало» по типу не ниже 0.60 и
не хуже «было»; иначе поставка только по решению владельца, с цифрами из отчёта.

Медоиды: не более 20 записей на метку с одной установки (детерминированно — первые по `recordId`),
поэтому одна большая библиотека не займёт все 8 прототипов.

### 3. Приложение

- `AdaptiveClassifier` получает `loadGlobalPrototypes(const juce::String& json)`. Глобальные
  прототипы хранятся рядом с локальными, с отрицательным `sampleId`.
- Приоритет: локальное подтверждение пользователя важнее общей модели. Оценка глобального
  прототипа умножается на 0.95 **до** порогов приёма, поэтому глобальному прототипу нужно сырое
  сходство ≥ 0.84 для типа и ≥ 0.89 для тега, чтобы вообще стать кандидатом. При разнице с лучшей
  локальной меткой до 0.02 побеждает локальная. Источник в кандидате: `user_adaptive` для
  локального и `global_adaptive` для глобального; при победе локального глобальный кандидат не
  добавляется.
- `SmartResolver`: `global_adaptive` получает приоритет сразу ниже `user_adaptive` и группу
  `adaptive` — ниже `dsp` и `asd_warp`, выше `path`.
- Теговые глобальные прототипы в этом этапе **не подаются** в AutoTag: иначе фоновая задача начнёт
  массово проставлять теги, выученные на чужих библиотеках, и декодировать аудио у всех. Теги
  остаются в файле прототипов и отчёте, для будущего этапа.
- `hasPrototypes()` остаётся про локальные; новые проверки не должны включать адаптивный путь
  AutoTag только из-за загруженного файла.
- `MainComponent` после `loadFromRepository` загружает `BinaryData::global_prototypes_json`.
  Файл лежит в репозитории, генерируется скриптом и коммитится перед выпуском; при нехватке данных
  это валидный файл с пустым списком меток, поэтому ресурс есть всегда и конфигурация не зависит от
  ручного шага. Ошибка парсинга — запись в лог и работа без глобальных прототипов.
- UI не меняется, кроме строки в About: «Global prototypes: <дата>, <число меток>».

### 4. Кандидаты в стандартные теги и типы

`services/training/candidates.mjs`:

- считает по датасету кастомные теги и типы, покрытие установок и частоту;
- отбрасывает опасные строки (пути, адреса, URL), числа, мусор длиной < 2;
- сопоставляет с существующими стандартными без учёта регистра и предлагает объединение;
- пишет `docs/tag-candidates.md` (владелец решает) и `candidates.json` для скрипта применения.

Порог для попадания в список: `installSupport >= 5` и не менее 1% установок.

Применение — только вручную и осознанно:

- тег добавляется в `standardTags` (`core/database/SampleRepository.cpp`) и в новый блок
  «schema 14 tags», чтобы существующие каталоги получили его при обновлении схемы;
- тип добавляется в таблицу алиасов `NameHeuristics` и в список стандартных типов;
- данные пользователя не переписываются (как в схеме 9): если такой тег уже есть у человека как
  свой, он остаётся его тегом со своим цветом, а `custom_types` и старые значения типа не
  трогаются; новый стандартный тег просто существует рядом;
- по каждому пункту — строка в `docs/TAG_PROMOTION.md`: имя, покрытие, решение, дата, версия схемы.

### 5. Публикация датасета (решение владельца)

Вариант A: держать датасет приватным в R2. Вариант B: публиковать обезличенный `dataset.jsonl` на
Hugging Face под CC0 как вклад в сообщество. В обоих случаях датасет и прототипы пересобираются из
R2 перед каждым выпуском, поэтому удалённые данные уходят из следующей версии. Для B нужен
отдельный скрипт и описание; в этот этап входит только подготовка, публикация — по решению.

## Проверка

- Node: `export` — надгробия, дубли, фильтр установок, отказ на плохом диапазоне; `training` —
  воспроизводимость файла побайтно, farthest-first на синтетике, leave-one-install-out на
  фикстуре; `candidates` — пороги и отбраковка мусора.
- C++ `[contribute][training]`: загрузка корректного JSON, отказ на битой длине вектора и чужой
  схеме, приоритет локального подтверждения над глобальным, источник `global_adaptive` в кандидате.
- Ручная проверка: сборка с реальным `global_prototypes.json`, Smart metadata на 20 файлах до и
  после, сравнение числа предложенных типов.

## Риски

- Мало данных на старте: прототипы появятся, но отчёт покажет низкую точность; поставка тогда
  добровольная. Цена ошибки — неверные предложения, а не порча каталога.
- Отравление данных: вес установки ограничен `installSupport`, прототип не строится по одной
  установке, выбросы не становятся медоидами.
- Рассинхронизация формы признаков: версия схемы в файле и в коде, тест на несовпадение.
- Ощущение «модель знает мою библиотеку»: глобальные прототипы — это числа без привязки к файлам;
  UI показывает источник и дату.

## Решения исполнителя (внесены после проверки плана)

- Базовая линия в отчёте — локальные прототипы установки без глобальных; «стало» — как в билде.
- Учимся только на строках `origin='user'`; машинные и старые строки не участвуют.
- Ресурс прототипов всегда есть в сборке, включая пустой; генерация коммитится.
- `typeIsCustom` исправляется: встроенный список — только канонические типы, пользовательский тип
  больше не выдаёт себя за стандартный.
- Штраф 0.95 применяется до порогов приёма; приоритет локального при разнице до 0.02.
- `global_adaptive` в резолвере — сразу ниже `user_adaptive`, группа `adaptive`.
- Глобальные теги не идут в AutoTag в этом этапе.
- Медоиды ограничены 20 записями с установки на метку.

   обучения, как рекомендую, или включить с пометкой в отчёте?
