# Smart catalog — foundation design (2026-11-07)

Статус: проектирование первого среза следующего этапа. Исходный HEAD — `9401802`.

## Задача

Сделать хранение и фоновую обработку smart-метаданных достаточно надёжными, чтобы
на них можно было строить колонки, фильтры, инспектор и ручные исправления.
Срез не добавляет DSP и не меняет UI-каталог; он убирает шесть ограничений,
перечисленных в ТЗ как обязательные для этапа.

## Решения

1. **Одна публикация.** Кандидаты, извлечения, fingerprints и итоговый результат
   пишутся одной транзакцией `BEGIN IMMEDIATE ... COMMIT`. Чтение файлов и
   вычисление результата выполняются до транзакции. Ошибка или отмена не
   меняет последнее завершённое поколение.
2. **Версии.** Хранятся отдельно: версия набора extractors, версия resolver и
   версия DSP. Результат содержит все три; несовпадение переводит его в `stale`.
   У каждого извлечения и кандидата есть собственные `extractor_id` и
   `extractor_version`, поэтому происхождение не смешивается.
3. **Поколение и ревизия.** `smart_meta` хранит монотонный счётчик поколений.
   Каждый результат имеет `revision`; публикация принимает ожидаемую ревизию и
   отказывается перезаписывать более новый результат.
4. **Fingerprints до и после.** Сервис снимает `size + mtime` всех зависимостей
   до извлечения и после. Если набор изменился, публикации нет: результат
   помечается `stale`, а не выдаётся за актуальный.
5. **Override отдельно от состояния.** `smart_overrides` не перезаписывается
   анализом. В `SmartResult` добавлены флаги `typeOverridden`, `bpmOverridden`
   и т. д.; состояние `*State` описывает только автоматический анализ.
   Действующее значение = автоматическое + применённый override.
6. **Структурированные ошибки.** Таблица `smart_failures` хранит код, сообщение,
   число попыток и время. Успешная публикация её очищает. Ошибка одного файла
   не останавливает очередь.
7. **Проверка устаревания.** Обычный проход выбирает результаты без записи,
   с другой версией, `stale` или `error`. Дополнительно он сверяет сохранённые
   fingerprints с текущими для уже завершённых результатов: изменение,
   появление или удаление sidecar обнаруживается при запуске прохода.
8. **Каталог.** Публикация проверяет, что репозиторий всё ещё указывает на тот
   же файл каталога, с которого задание началось.
9. **Никаких процентов уверенности.** Уверенность не хранится числом. Вместо неё
   хранятся источник, версия, ограничение и конкурирующие кандидаты. Степень
   согласия вычисляется resolver-ом из групп источников.

## Модель данных (схема 7)

Новые колонки:

- `smart_results`: `revision`, `pipeline_state`, `extractor_version`,
  `resolver_version`, `dsp_version`, `generation`, `analyzed_at`, `error_code`,
  `error_detail`, `type_overridden`, `structure_overridden`, `bpm_overridden`,
  `key_overridden`, `root_overridden`, `pitch_overridden`, `pitch_midi`,
  `pitch_cents`, `pitch_state`, `pitch_source`.
- `smart_candidates`: `extractor_id`, `extractor_version`, `raw_value`,
  `input_kind`, `input_path`, `fingerprint`, `aux_value`, `limitation`.
- `smart_inputs` без изменений.
- Новые таблицы: `smart_extractions`, `smart_failures`, `smart_meta`.

Миграция с v6 делает резервную копию через SQLite backup API, добавляет колонки
и таблицы, сохраняет sample IDs, теги, звёзды, basic features, duplicate groups
и overrides. `basicFeaturesVersion` остаётся 1: Phase 1 не пересчитывается.

## Resolver

- BPM: 20–400; значения в пределах 1 BPM согласованы; расхождение — конфликт.
  Отношение ~2× (half/double) — `ambiguous`, а не конфликт. `variableTempo`
  не сводится к одному числу.
- Key: энгармонические варианты одной высоты не конфликт; relative major/minor —
  разные трактовки (`ambiguous`); неизвестный mode не дополняется.
- Pitch: отдельное поле кандидатов; sampler root никогда не становится key.
- Override применяется после автоматического результата и не стирает его
  состояние и объяснение.

## Сервис

- Режимы: инкрементальный проход по всему каталогу и очередь выбранных файлов.
- Pause / Resume / Cancel, ограниченная очередь, отмена внутри длительного чтения.
- Прогресс: этап, всего, обработано, ошибки, устаревшие, текущий файл.
- `refreshSample()` остаётся синхронным только для тестов и worker-потока;
  из UI используется постановка в очередь.

## Вне среза

DSP BPM/pitch/key, taxonomy, UI-колонки, инспектор, глобальные фильтры и
сортировка. Для них подготовлены поля и версии, но поведение не заявляется.
